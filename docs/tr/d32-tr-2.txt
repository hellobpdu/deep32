Abstract

   D32-TR-1 described how Deep32 is built.  This report measures it.  It
   covers release 0.1.0-alpha.3 and brings together three kinds of
   evidence: the retrieval evaluation on 696 labelled questions, the
   recorded telemetry of four research answers produced through the Ask
   window, and a blind comparison of Deep32 with three general
   assistants on three hard routing benchmarks.

   In the blind comparison all four systems derived the core results
   correctly.  Deep32, answering from its local corpus with web search
   disabled and with gpt-6.2-sol as its headend model, scored 268.5 of
   300 under the headline rater against 270 for Claude with web
   research, and its answers carried the most checkable evidence (69 of
   75); Gemini and ChatGPT scored 226 and 211.5.  A second blind rater
   agreed within 2.3 points per answer, and an earlier grading with the
   names visible is listed beside them.  Deep32 is the only system that
   every grader placed first or second, and it answered in 8.5 minutes
   on average.  The comparison is small and its limits are stated with
   it.

   Every number in this report is labelled by where it comes from: the
   source code, a log or build record, a calculation on recorded values,
   or the author's judgement.  Where the record is missing, the report
   says so.  The limits of the evidence, and the evaluation still to be
   run before a beta, are stated in full.

1.  Introduction

   Deep32 lets an agentic language model answer networking questions
   from a local corpus of RFCs and vendor documentation, and check its
   quotations against the stored text [D32-TR-1].  The design report
   explains how.  Three questions remained open after it:

   *  How well does the retrieval pipeline put the right passage in
      front of the model?



Cummings                      Informational                     [Page 2]

                           Deep32 Measurements             November 2026


   *  What does the model actually do with eleven tools when it
      researches a hard question?

   *  Are the answers better than those of capable assistants that
      search the open web?

   This report answers the first two with recorded measurements, and the
   third with a blind comparison that is small and is described with its
   limits.  Release 0.1.0-alpha.3 [DEEP32] is the system measured.

1.1.  How Evidence Is Labelled

   Each statement of fact carries one of four labels:

   [Code]  Read from the source code or the shipped configuration of the
      release.
   [Record]  A value written by the system itself: a log, a build
      report, a database count.
   [Calc]  Arithmetic on recorded values; the method is given.
   [Judgement]  The author's assessment, including the grading in
      Section 6.

1.2.  Terminology

   Run  One question asked through the Ask window and answered, from
      submission to the end of the answer.
   Model request  One call from the headend to the hosted model.  A run
      makes many.
   Tool call  One call of one of the eleven Deep32 tools, such as
      get_section or verify_quote.
   Context  The tokens the headend sends with one model request:
      instructions, tool definitions, the question and everything
      researched so far in the run.
   Headend  The program that runs the model for Ask: here, a relay on
      the user's PC that starts the Codex app-server for each turn.

2.  System Under Test

   The measured deployment is release 0.1.0-alpha.3 at update sequence
   4, on the three machines D32-TR-1 describes: the Workstation
   (OpenBSD), which holds the corpus, the indexes, the engine, the
   gateway and the Ask window; the Forge, a GPU host that computes query
   embeddings and reranker scores; and the headend PC, which runs the
   relay.  [Code]

   Every tool call goes from the model, through the relay and the pinned
   D32U/1 link, back to the Workstation's own gateway and engine.  The
   PC holds no index.  [Code]



Cummings                      Informational                     [Page 3]

                           Deep32 Measurements             November 2026


   Changes since D32-TR-1 that bear on the measurements:

   *  The top eight hits of a search now carry up to 3,200 characters of
      text instead of 2,400.  [Code]

   *  The default answer depth caps its search rounds by search size:
      Full 4, Half 5, Light 6, plus one batch of quotation checks.
      D32-TR-1 described at most three rounds.  [Code]

   *  The engine serves one search at a time with a queue of 16, behind
      a first-in, first-out gate for the reranker.  [Code]

   *  Quotations with omissions are checked part by part within one
      section, each part at most 300 characters after the previous one.
      [Code]

   *  The Ask headend runs a fresh, isolated Codex app-server process
      for every turn, read-only, with shell, web search and automatic
      delegation to other agents disabled.  Before it serves any tool
      call it checks the process's configuration, its feature flags, its
      tool list (exactly eleven tools) and its model list.  [Code]

   The hosted model in every measured run was gpt-6.2-sol.  One run used
   the reasoning effort "max" and three used "ultra".  Because the
   headend disables delegation, "ultra" runs at the same reasoning depth
   as "max" in this setting.  [Code] [Record]

4.  Retrieval Quality

   The retrieval evaluation of D32-TR-1 is restated here because it
   remains the strongest measurement of the system. 696 answerable
   questions, each with its relevant passages labelled in the source
   text, were run through the gateway on 2 November 2026, against the
   release 0.1.0-alpha.2 design and an earlier corpus generation; it was
   not repeated on the deployment measured in Section 5, which differs
   in the width of the top hits, in serving one search at a time, and in
   searching vectors exactly rather than through an approximate index.
   Searches fuse a BM25 and a dense ranking by reciprocal rank fusion
   [RRF] and rerank the first 15 candidates with a cross-encoder.  A
   question is a hit at rank k when a labelled passage is among the
   first k results.  [Record]

   Paired over the 696 questions, reranking won 102 questions and lost 9
   at rank 1, and won 6 and lost none in the top eight.  The mean
   reciprocal rank at 10 rose from 0.882 to 0.970.  Of the 31 questions
   still missed at rank 1, 7 had an answering passage that carried no
   label, 21 were reranker misorderings, and 3 left the relevant passage
   outside the reranker's first 15 candidates.  [Record]

   Three limits apply.  The questions were written with a language model
   and labelled from pooled results; two small blind audits agreed with
   the labels on 22 of 27 and 15 of 16 items; and the 30 out-of-scope
   questions of the set have no reported result.  Retrieval quality is
   also not answer quality: a hit puts the right passage in front of the
   model, and the answer can still misuse it.  [Record]

5.  How an Answer Is Researched

   Four runs were recorded on 23 November 2026: an introductory OSPF
   question ("Explain OSPF from the ground up ...", with the modifiers
   d, v, o and g) and Benchmarks 001 to 003 of Section 6.  The benchmark
   answers were kept by hand; their link to the logged runs rests on run
   order and the author's record.  The relay and the Codex app-server
   logged every tool call, every turn's token use and, for the last run
   in full, the context of every model request.  [Record]

6.  Answer Quality: A Blind Comparison

   Three benchmarks, written by the author, test whether an answer can
   derive results from protocol rules rather than recall them.  Deep32
   and three general assistants each answered all three once, and every
   answer was graded blind, by two raters, against an answer key solved
   first from the question and the standards.  [Judgement]

6.1.  Benchmarks

   Benchmark 001  OSPFv2 external route selection: five Type 5 LSAs for
      one prefix at an ABR, with forwarding addresses, ASBR entries in
      two areas and both settings of RFC1583Compatibility.  Eight
      questions: eligibility, the selected route under each setting,
      three variants, ECMP, the order of evaluation and verification
      commands by layer [RFC2328].

   Benchmark 002  BGP route-reflection oscillation: two route
      reflectors, three exits in two neighbouring ASes, MED and IGP
      cost.  Nine question groups: proof that no stable state exists,
      the IGP-cost threshold at which one appears, always-compare-med,
      four ADD-PATH cases, forwarding deflection, identical cluster IDs
      and configuration [RFC4456].

   Benchmark 003  An MPLS L3VPN escalation: overlapping routes in two






Cummings                      Informational                     [Page 9]

                           Deep32 Measurements             November 2026


      VRFs, an OSPF sham link and backdoor, PE-CE domain IDs and the DN
      bit, label traces through a failure and a micro-loop, a routing
      feedback loop, and ten conflicting operator reports to reconcile
      [RFC4364].

   Only Deep32's settings are recorded by the system.  The settings of
   the other three are those I selected in each application; the answers
   show web use (links to RFC Editor, Cisco and community pages) but
   carry no record of model or date.  The conditions are not matched:
   the general assistants could search the whole web, and Deep32's
   question carried four modifier sentences asking for deep research, a
   long answer, verification steps and troubleshooting.  The comparison
   is between systems as an engineer would use them, not between models.

   The answers were captured as text: copied from Deep32, Claude and
   ChatGPT, and converted from Gemini's PDF exports.  Two capture
   effects matter.  ChatGPT's citations, links in its own interface,
   survive in the copy only as opaque markers; and the PDF conversion
   fused some of Gemini's footnote numbers into values and broke some
   tables.

6.3.  Grading

   1.  Masking.  Each benchmark's four answers were given the letters A
       to D in a different order, system names were replaced, and the
       Deep32 question line was removed.  The key to the letters was
       held apart from the raters.



Cummings                      Informational                    [Page 10]

                           Deep32 Measurements             November 2026


   2.  Key first.  The first rater solved each benchmark from its
       question alone, with the derivation, the governing rule and its
       source line for each item, before opening any answer.

   3.  Sources.  Facts could come only from the question, the RFC and
       Cisco texts of the corpus (read as plain files, not through
       Deep32), and arithmetic.  No web and no facts from memory: vendor
       behaviour that those texts do not document was marked
       unverifiable and neither rewarded nor penalised.

   4.  Scoring.  Correctness 40 (agreement with the key), evidence 25
       (primary, specific citations that say what the answer claims,
       spot-checked against the texts), completeness 15, caution 10
       (assumptions, release qualification, labelled inference) and
       clarity 10.

   5.  Re-check.  The first rater then tried to refute its own key on
       every point where the answers differed.  No key item changed.

   6.  Second rater.  A second rater, a different model, scored the same
       masked answers on the same rubric against the same key, without
       seeing the first scores, and was asked to show any key item wrong
       from the RFC text.  It upheld every item.

   The first rater was Claude Opus 5.5 and the second Claude Mythos 5.2,
   each run as a separate instance per benchmark, working from files.  I
   take the second rater's scores as the headline: it is the stronger
   model, and it scored against a key that had by then been solved, re-
   checked and upheld.  The first rater's scores are given beside them.

   A third set of scores predates this grading.  ChatGPT (GPT-6) scored
   the same twelve answers with the system names visible, by its own
   criteria and without the key.  Those scores are listed in Table 9 for
   comparison.  They are not blind and carry no weight in the
   conclusions.

6.5.  What Decided the Scores

   All four systems got every core computed result right in all three
   benchmarks: the eligible LSAs and selected routes of 001, the absence
   of a stable state and the threshold of 002, the cost ranges, the TTL
   trace of the micro-loop and the minimum set of false reports of 003.
   None fell into the planted traps, such as using the reflector's
   router ID in the tie-break of 002.  Correctness spans 12 points of
   120 under the headline rater and nine under the first.  The scores
   were decided by evidence, by errors outside the core results, and by
   completeness.  [Judgement]

   Evidence.  Every citation the two raters checked in a Deep32 answer
   matched the corpus text at the cited document and lines; a few
   pointed at passages that fit the claim only loosely.  Claude quoted
   RFC and Cisco text exactly by section, without line numbers, and
   every checkable quotation matched; some rested on documents outside
   the corpus, such as RFC 3345.  Gemini mixed primary sources with
   forums, blogs and links its export left as "unknown_url".  ChatGPT's
   citations could not be resolved from the text.  [Judgement]

   Errors outside the core results, by system:

   *  Gemini: that disabling RFC1583Compatibility also changes the
      summary-cost calculation (001); "MUST NOT" for the "should not
      assume" of RFC 7911 (002); that RFC 4577 copies the MED into the
      Type 3 metric (003); and a Cisco command's effect on DN-bit checks
      stated from another platform's note (003).

   *  ChatGPT: an ECMP rationale built on a wrong premise about the
      associated area of external paths (001); a cycle summary that
      skips a state (002); a wrong section number (003).

   *  Claude: none affecting a result.  It was the only system to point
      out that Benchmark 003 contains an equal-cost tie that contradicts
      its own "no ECMP" premise.

   *  Deep32: none affecting a result.  It lost points for configuration
      given as templates, a thin treatment of the operational effects in
      002, and leftovers of its working process in the answer text
      ("Full search, deep mode.", "I'll verify ...").

   Leaving clarity out of the headline totals puts Deep32 ahead of
   Claude, 247 to 243.  Leaving evidence out puts Claude ahead, 214 to
   199.5.  Deep32's place at the top rests on its evidence, and its
   shortfall against Claude is in detail of correctness, completeness
   and clarity.  [Calc]

6.6.  The Headend Model

   Deep32 does not write its answers; its headend model does.  In these
   runs the headend was gpt-6.2-sol at effort ultra, so the Deep32
   scores are those of that model working through Deep32's tools and
   corpus.  Another headend would give other answers and other scores.
   [Record]

   ChatGPT, a model of the same vendor researching on the open web,
   scored 57 points lower than Deep32 under the headline rater (211.5
   against 268.5) and 52 lower under the first rater.  Most of the
   difference is evidence, 25 against 69, and part of that is the
   capture effect described in Section 6.2.  The two are different
   models with different instructions, so the gap is not a controlled
   measure of what the corpus and the tools add.  The matched-model arms
   planned in Section 10 are designed to measure that.  [Calc]
   [Judgement]

6.8.  Threats to Validity

   *  Both blind raters are Claude models, and one of the systems
      compared is Claude.  Names were masked, but style can identify a
      model.  Deep32's headend model, gpt-6.2-sol, is not from
      Anthropic.

   *  Each family of grader placed first a system whose answers a model
      of its own vendor wrote: the Claude raters placed Claude first,
      and the GPT grader placed Deep32 first.  Only the blind raters
      scored against a key.

   *  Masking was weaker for Deep32 than for the others: its answers end
      with the list of sections read and cite corpus documents by key,
      which a rater can recognise.








Cummings                      Informational                    [Page 16]

                           Deep32 Measurements             November 2026


   *  Evidence was checked against the RFC and Cisco texts that Deep32
      indexes.  Answers that cite those texts by line are easier to
      confirm, and web sources outside them could only be marked
      unverifiable.  This favours Deep32's evidence score, although an
      unverifiable source was not counted against an answer.

   *  Capture lowered ChatGPT's evidence and Gemini's clarity scores
      (Section 6.2).  Their totals should be read with that in mind;
      their correctness and caution scores are not affected.

   *  Two blind raters, one answer per system, three benchmarks.  The
      second rater scored against the first rater's key, so the two are
      independent in scoring and not in the key.  The difference between
      the top two is smaller than the difference between the raters.

   *  Deep32's result is that of one headend model at one effort setting
      (Section 6.6).

   *  Only Deep32's answer times are measured.  The other three are
      estimates (Section 6.7).

7.  Evidence in the Answers

7.1.  One Answer in Detail

   The introductory OSPF answer (the first run) is the one whose full
   text and full telemetry are both on record.  It cites 17 source
   documents, all primary: four RFCs (2328 [RFC2328], 3101, 5340, 5838),
   six Cisco configuration guides and command references pinned to the
   Catalyst 9300 17.9 release, and seven Cisco TechNotes.  It carries
   about 107 citations to a document and line range, and 18 quotations:
   14 marked exact and 4 marked normalized, against 18 accepted
   quotation-check calls.  Its last lines list every section it read.
   [Record]

   It also found a contradiction in Cisco's own guide: one passage gives
   the OSPF reference bandwidth as "10" and another as 100 Mbps.  The
   answer quoted both, preferred the default table and the command
   reference, and told the reader how to check a live device.  [Record]

7.2.  What "Verified" Means

   verify_quote looks for the quotation in the stored source text of the
   cited document: first verbatim and case-sensitive, inside the cited
   section and then anywhere in the document; failing that, after
   mapping typographic quotes and dashes and removing whitespace and
   hyphen runs.  It returns where it matched, by section and source
   line.  [Code]



Cummings                      Informational                    [Page 17]

                           Deep32 Measurements             November 2026


   A label of exact or normalized therefore proves that the words exist
   in the source, and where.  It does not prove that the passage
   supports the sentence it is attached to, and most claims in an answer
   are paraphrases with a citation, which no mechanism checks for
   support.  An optional script on the relay compares an answer's
   quotations, RFC citations and specific values with what its tool
   calls returned; it was off in the measured deployment.  [Code]
   [Record]

9.  Limitations

   *  The comparison in Section 6 is three benchmarks and one answer per
      system, graded by two raters of one model family.  It is evidence,
      not a ranking that would survive a larger study.

   *  The benchmark answers of the other systems were produced in their
      own applications with web access; their models, settings and dates
      were not recorded with the same care as Deep32's.

   *  No answer was tested on a router.  Correctness was judged against
      an answer key derived from the questions' own data and the RFC and
      Cisco texts of the corpus.

   *  The relay does not keep question texts, answer texts, tool
      arguments or the result of each quotation check.  The three
      benchmark answers were kept by hand; their association with the
      logged runs rests on run order and the author's record.

   *  Codex keeps only its last 1,000 log rows per thread, so the per-
      request record is complete for one run of four.

   *  Release metadata is missing on 320 of 489 Cisco documents, mostly
      TechNotes; release pinning cannot act on them.

10.  Evaluation Plan for the Beta

   The beta release waits on a claim-level evaluation designed to remove
   the limits above:

   *  40 to 60 held-out questions, stratified by kind (defaults and
      timers, command syntax at a release, RFC against Cisco behaviour,
      troubleshooting, design), each with a reference answer split into
      atomic claims and their sources.

   *  The same model and effort in every arm: Deep32; the same model
      with no tools; the same model with plain dense retrieval over the
      same chunks; and ablations of reranking, section reads and
      quotation checks.







Cummings                      Informational                    [Page 19]

                           Deep32 Measurements             November 2026


   *  Scores for correctness, support of each claim by its cited
      passage, citation precision, release qualification and calibrated
      refusal; graded blind by two judges, with disagreements and a
      random fifth adjudicated by a person.

   *  Paired analysis by question with effect sizes and bootstrap
      intervals; every question, answer, tool call and quotation result
      kept with the run.

   The gates set for the beta are at most 2 % fabricated claims, every
   out-of-corpus probe refused, and every printed citation exact.

11.  Security Considerations

   The hosted model sees the question, the retrieved passages and its
   own reasoning; nothing else leaves the user's machines.  Retrieved
   text can carry instructions; the tools mark it as data and the model
   is told to treat it so, but a passage can still steer the model
   within the eleven tools.  The measurements in this report were taken
   from logs that hold no question or answer text, and local collections
   outside the release are not described.

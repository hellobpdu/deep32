# asklink: the node side of D32U/1 (d32-chatd, d32-chatctl)

Lane **asklink** of the Deep32 Workstation (OpenBSD 8.0). Item 41: Deep32 Library is the one front door; its Ask room
talks to **d32-chatd**, the chat broker, over a local UNIX socket. The UI process has no network. The broker alone
holds the D32U/1 link to the paired Windows relay (or hub), and that link carries queries only.

**Normative contract:** the accepted spec on branch `relay/d32u1`, commit `cbe83b7`, in
the relay repository's `docs/spec/` (`d32u1.md`, `sas.md`, `schemas/`, `sas-vectors.json`,
`frame-vectors.json`). A read-only snapshot is in `tests/spec/`; the tests read the vectors from there. That worktree
was never edited.

## Processes

| Process | User | Confinement | Job |
|---|---|---|---|
| parent | root | unveil state dir `rwc` + own binary `x`; pledge `stdio rpath wpath cpath fattr unix proc exec` (`rpath`: `rename(2)` of the atomic pin write needs it); `RLIMIT_CORE` 0 | config, node identity, pins (0600), root-only control socket for `d32-chatctl`, the ceremony's words (computed and checked here), restarts (more than 3 child deaths in 10 min isolates the uplink) |
| `ui` | `_d32chat` (3218) | chroot `/var/empty`, pledge `stdio unix` | `uplink.sock` (0660 root:`_d32users`, FIX-16): newline-delimited strict JSON for the Library UI |
| `link` (one per relay) | `_d32upw` (3217, work) / `_d32uph` (3216, hub) | chroot `/var/empty`, pledge `stdio inet` | the D32U/1 client (libtls, TLS 1.3, mutual, pinned); codex-ctl; mcp forwarding to the local deep32-gateway |

The children re-exec the daemon with exactly `-P <role> -I <n>` (any other argument vector aborts) and get fixed
descriptors: 3 = parent, 4 = role socket, 5.. = ui-to-link pairs. They talk over imsg (libutil, 7.7+ API). The
parent never parses client input. Logs use fixed formats with numeric arguments only (no `%s`, no peer text).

**Restarts.** The parent's ends of the child sockets are non-blocking, and the parent never flushes them with a
blocking call. When a child dies:
1. The parent reaps it and SIGTERMs the others. A child still alive after 2 s is SIGKILLed; this is bounded and
   never signals a pid the parent has already reaped.
2. It tells a console that was waiting on a ceremony (RELAY_LOST).
3. It restarts every child, then polls again: it never acts on events from the descriptors it just closed.
4. The fourth death in ten minutes leaves the uplink ISOLATED (no children) until a local restart. Status still
   answers, and SIGTERM still ends the parent.

A link child that breaks the imsg contract is killed, which counts as a death, rather than taking the parent down.

## Configuration (`/etc/d32/chatd.conf`)

```
node-id         workstation
state-dir       /etc/d32/state/chat          # node.key 0600, node.crt, <link>.pin 0600, edge.token 0600
control-socket  /var/run/d32/chatd.sock      # 0600 root: d32-chatctl
ui-socket       /var/run/d32/uplink.sock     # 0660 root:_d32users: the Library UI
ui-group        _d32users
ui-user         _d32chat
edge            127.0.0.1 8766 /mcp          # the node's local deep32-gateway (loopback only)
edge-token-file /etc/d32/state/chat/edge.token
link work relay <relay tailnet IP> 7452 user _d32upw class research-relay
```

Relay addresses are IP literals (the link child has no DNS). A trailing `tls12` on a link line records the local
operator's decision that the relay cannot offer TLS 1.3; there is no automatic downgrade.

## Pairing (node half)

`d32-chatctl keygen` creates the node identity (ECDSA P-256, self-signed; the pin is the trust anchor).
`d32-chatctl pair work` opens a five-minute window that allows one unpinned connection attempt. The tool refuses to
run off the wscons console (`ttyname(0)` must match `/dev/ttyC[0-9]+`). That is an operator-safety guard in the
tool, not a boundary: d32-chatd accepts the request from any uid-0 peer on its 0600 root socket, and root can
bypass any such check anyway.

The link child sends the parent its offer: the relay's HELLO id, the relay's certificate pin and both HELLO nonces.
The **parent computes the ten words itself** from the node pin and that offer, and the tool shows them as `01 WORD`
to `10 WORD`. The tool then reads the ten words typed from the relay's screen; the parent keeps a copy and forwards
them. The link child checks them and sends PAIR_CONFIRM. After both confirmations it asks the parent to persist the
pin. The parent writes `<link>.pin` (the relay's DER SHA-256 and its HELLO id, 0600) only when all of these hold:
- the console window is still open;
- the pin and the id are exactly the ones the words were computed for;
- the typed words match the parent's own code.

So a compromised link child cannot pin a relay of its choice: that would need a 110-bit SAS collision with the real
relay's screen. Then come both PAIR_COMMITs and the link goes ACTIVE. A changed certificate or a different HELLO id
for a stored pin is refused until `d32-chatctl unpair work`, which deletes the pin and drops the link at once.

## UI API (`uplink.sock`)

Requests: `{"op":"status"}`, `{"op":"session.open"[,"link","model","effort"]}`,
`{"op":"turn.start","session","text"}`, `{"op":"turn.interrupt","session"}`, `{"op":"session.close","session"}`,
`{"op":"channel.open","channel":"seal|lib|sync"}` (always refused on this contract).
Events: `status`, `link`, `session.opened`, `agent.delta`, `agent.final`, `turn.completed` (status, usage),
`error` (D32U code; 11 = RELAY_LOST), `session.closed`, `mcp` (the RAG ledger: method, tool, result, bytes, ms),
`channel.refused`. Relayed text is stripped of C0/C1 controls except LF and TAB.

- A `session.open` the link cannot honour (link down: 11; limits: 5; bad model or effort: 7) gets `error` and then
  `session.closed`, and the ui child forgets the session id it reserved.
- Ledger `result` values: `ok`, `error`, `refused` (-32601, never reached the edge), `budget` (hourly cap) and
  `cancelled` (the session ended while the call was at the edge).

**Session end and mcp streams.** When a session ends, by the UI's `session.close`, by the UI going away, or by the
relay's CLOSE or RESET of channel 1, no mcp stream keeps a pointer to it:
- A stream whose request has arrived is RESET 10 (CANCELLED) and freed. Its edge call is abandoned, and nothing more
  is sent on it.
- A stream still waiting for its request is detached. That request then gets RESET 7 (SESSION) and never reaches the
  edge. Resetting it at once could make the relay's request DATA land on a retired id, which d32u1.md makes fatal.

**Sessions per connection.** The relay allows 16 sessions over a connection's lifetime (`usedSessions`). Once all
16 are used and none is live, the link reconnects at once, with no ERROR, so that the next Ask conversation works. A
17th open while a session is still live gets LIMIT (5).
